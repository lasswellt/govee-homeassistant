## 1. #222 — silent-session check never arms on an H5310-behind-H5044 account

### Root cause (proven from code + reporter's numbers)
- The check only fires when `_mqtt_queries_since_connect >= MQTT_SILENT_MIN_QUERIES` (coordinator.py:3888, const.py:296-297). The counter is only incremented inside the status sweep after a publish (coordinator.py:3531-3532).
- Sweep targets = devices in `self._devices` that have an entry in `_device_topics`, are not groups, not quarantined, not in `MQTT_STATUS_QUERY_EXCLUDED_SKUS` (coordinator.py:3406-3425).
- `_device_topics` comes from `GoveeAuthClient.fetch_device_topics` (coordinator.py:2262-2273): legacy list topics (`_extract_topics_from_devices`, api/auth.py:621-654, used at :792) merged with BFF-only topics (api/auth.py:797-808). `gateway_routes` (api/auth.py:657-707) is a separate map: sub-device -> its gateway's `{device, sku, topic}`.
- Reporter: `device_topic_count: 1`, `gateway_route_count: 1`, accounts devices are the H5310 (via H5044) and an offline H5075; H5310 `transport_health.mqtt.last_sent: null`, quarantine empty. If the H5310's own id held the topic it would be a sweep target (H5310 is not in the exclusion list, const.py:441), so the single topic belongs to **the H5044 hub or the H5075**, not the H5310. The H5310's only MQTT knowledge is its gateway route. The H5044 is not in `self._devices` (BFF thermo hubs live in `_bff_thermo_hubs`, coordinator.py:605-608, registered only for `via_device`, :2851+), and the H5075 is excluded. Target list is empty -> counter stays 0 -> `_async_check_mqtt_silence` returns at :3888 every session, and since it does not re-arm (one-shot `async_call_later`, :3864), it is never evaluated again on that session.
- Diagnostics do not say whose topic it is (diagnostics.py:348-350 only counts). Proof of which device owns the topic needs a per-device `has_topic` flag (see task).

### Should the H5310 be a status-poll target? No.
- The H5310 is a BLE sensor bridged by the H5044, the same class as every SKU in `MQTT_STATUS_QUERY_EXCLUDED_SKUS` (const.py:406-441): those have a topic and "never answer a direct status-query publish ... AWS closes the session every single time" (#195, #237). Giving it a target would only add session drops.
- Querying the **hub's** topic (gateway route topic) instead: unverified on hardware. Nothing in the code base has ever sent a status query to an H5043/H5044 (they are never in `_devices`), so its behaviour is unknown and the #195 failure mode (session closed ~1-5 s after the query) is a real risk on an account whose only push channel is that hub. Rejected as the primary design; at most a later opt-in experiment.

### Positive evidence that does not break the design rule
The hub *pushes* every H5310 reading on the account topic as a `multiSync` thermo frame (api/mqtt.py:1057, decoded by `_handle_thermo_frame`, coordinator.py:3591-3620), measured ~8 min **before** the cloud copy lands in the BFF list (coordinator.py:2738-2752, #151). This account received those frames until 2026-09-26 (issue body). So: a BFF reading for a gateway-bridged thermometer whose device-side `lastTime` is newer than the session start, while the session has had zero inbound messages, is a push that Govee sent and the session did not deliver. That is a prompt-with-no-answer, exactly what the 3-query rule stands for, so the rule "silence without a prompt is not evidence" still holds.
- `lastTime` is already parsed (api/auth.py:161 -> `last_time` epoch ms) and compared to frame stamps in `_bff_reading_is_stale` (coordinator.py:2514-2528). Readings are applied in `_refresh_bff_thermometers` (coordinator.py:2680+); `_note_thermo_slot` (:2530-2543) proves the device is frame-routable (hub id + sno known).

### Recommended design: count "missed gateway pushes" as a second evidence source
1. const.py: `MQTT_SILENT_MIN_MISSED_PUSHES: Final = 2` (two hourly readings, so one cloud-side hiccup is not enough).
2. coordinator.py `__init__`: `self._mqtt_missed_pushes_since_connect = 0`, `self._bff_last_time_seen: dict[str, int] = {}`.
3. `_arm_mqtt_silence_check` (:3857) also resets `_mqtt_missed_pushes_since_connect = 0`.
4. New `_note_bff_push_evidence(device_id, sensor)` called from `_refresh_bff_thermometers` for each sensor with a hub id and `sno` (frame-routable) whose `last_time` is strictly greater than `_bff_last_time_seen[device_id]` (first sighting only seeds the map) and whose `last_time // 1000` is after the session's connect wall-clock time (`client.connected_since`, api/mqtt.py:442) plus a short margin. If `client.inbound_total == self._mqtt_inbound_at_connect`, increment the counter; then, if the session has been up >= `MQTT_SILENT_CHECK_DELAY` and the counter reached the minimum, schedule the silent handling.
5. Split `_async_check_mqtt_silence` (:3873-3902): keep the gate (connected, no inbound) and move the "reconnect once, then `async_create_mqtt_silent_issue`" tail into `_async_handle_silent_session(reason)`. Gate becomes `queries >= MQTT_SILENT_MIN_QUERIES or missed_pushes >= MQTT_SILENT_MIN_MISSED_PUSHES`. Warning text gains the evidence kind ("%d gateway readings reached the cloud but not this session").
6. Because the timer is one-shot, the BFF path itself must trigger the handling (step 4) rather than relying on the 1800 s timer; guard with a `_mqtt_silence_handling` flag so the timer and the BFF path cannot run it twice. The reconnect resets the counters via `_on_mqtt_connected` -> `_arm_mqtt_silence_check`, so the repair needs 2 more missed pushes on the new session (~2 h) — matches the existing "reconnect once, then repair" contract.
7. Diagnostics: add `missed_gateway_pushes_since_connect` next to the query counter, and a per-device `has_mqtt_topic` / `has_gateway_route` boolean (no topic strings) so the next report proves whose topic is the single one.
8. Repair text: `strings.json:728` (`mqtt_silent`) says "although the integration asked the devices for their status several times" — false for push evidence; reword evidence-neutral ("although Govee received new readings from your devices or was asked for their status") in strings.json and translations/en.json.

Tests (tests/test_issue_222.py): BFF reading newer than session start + zero inbound twice -> reconnect once; again on the new session -> repair; any inbound message in between -> no action and `_note_mqtt_inbound` clears; reading older than session start / same `lastTime` repeated / first sighting -> no count; device without hub/sno -> no count; sweep off (`MQTT_STATUS_POLL_OFF`) still raises via push evidence (the rule is about prompts, not the sweep); no MQTT client -> no-op.

### Rejected
- Make the H5310 a target via its own or a synthesized topic: #195-class session drops (const.py:406-441).
- Query the H5044 topic: unverified, risks closing the only push session; nothing in code has ever done it.
- Lower `MQTT_SILENT_MIN_QUERIES` to 0 / time-only silence: breaks the design rule (quiet accounts with the sweep off would get a false repair).
- Developer-API REST value changes as evidence: the Developer poll has no device-side timestamp, so a changed value cannot be tied to a push that should have arrived; the BFF `lastTime` can.
- OpenAPI event channel as evidence: separate MQTT session (api/openapi_events.py), proves nothing about the AWS IoT one.

## 3. #266 — H5194 probe 4 rarely updates

### Root cause
`_poll_probe_thermometers` (coordinator.py:3345-3366) sends, per armed device and per probe, `build_probe_read_packet` then `build_limits_read_packet` back-to-back (:3364-3365) through `BlePassthroughManager.async_send_ble_packet` (ble_passthrough.py:57-85), which has no pacing of its own. H5194 = 8 ptReal publishes in one burst; probe 4's reading is 7th. Reporter's `recent_probe_frames` count: probe 4 `0x24` replies 0 -> 11 with pacing. H5192 = 4 packets (`probes_for_sku`, api/probe_thermometer.py:110-112).

### Design
- const.py next to `DEFAULT_PROBE_POLL_INTERVAL` (:278) / `MIN_PROBE_POLL_INTERVAL` (:308): `PROBE_PACKET_SPACING: Final = 1.0` (seconds between two probe packets; the reporter's tested value, same as `MQTT_STATUS_QUERY_SPACING`, const.py:393) and `PROBE_LIMITS_READ_EVERY: Final = 6` (limits on every 6th tick).
- coordinator `__init__` (near :645-646): `self._probe_poll_tick = 0`, `self._probe_poll_task: asyncio.Task[None] | None = None`.
- `_poll_probe_thermometers(self, device_ids: Iterable[str] | None = None, *, read_limits: bool | None = None)`: per device, all temperature reads first, then (when `read_limits`) all limit reads; `await asyncio.sleep(PROBE_PACKET_SPACING)` **between** packets (not after the last). After each sleep re-check `client.connected` and that the device is still in `_probe_polling_enabled` (disarm mid-sweep stops it). `read_limits=None` means "this tick decides": `self._probe_poll_tick % PROBE_LIMITS_READ_EVERY == 0`, then increment the tick once per sweep. Tick 0 reads limits, so the first sweep after setup populates the number entities.
- `set_probe_polling(enabled=True)` (:3310-3322): immediate read only for the newly armed device with `read_limits=True`, so its limit numbers fill at once regardless of the shared tick.
- Re-arm: `_probe_poll_callback` (:3339-3343) measures the sweep with `time.monotonic()` and arms the next timer at `max(PROBE_PACKET_SPACING, interval - elapsed)`; add an optional delay arg to `_schedule_probe_poll` (:3333-3337). This keeps the user's interval as the true cadence (H5194 limits tick: 7 s of spacing on a 10 s minimum interval) and cannot overlap, since the re-arm still happens after the sweep.
- Run the timer's sweep as a tracked task like `_bff_poll_task` (coordinator.py:639, 3973-3975): the callback does `self._probe_poll_task = self._config_entry.async_create_background_task(...)`. `async_shutdown` (:6518, probe block :6538-6541) also cancels `_probe_poll_task` and clears `_probe_polling_enabled`, so a sweep that is sleeping cannot keep publishing or re-arm after unload.
- H5192: 2 reads + 1 s; limits ticks 4 packets + 3 s. Harmless.
- Limits staleness: a limit changed on the base station or in the app now shows within 6 ticks (3 min at the default 30 s, 1 min at 10 s); writes from HA already read back immediately (`async_set_probe_limits`, test at tests/test_cov_coordinator_setup.py:1506-1512). Update the docstring at :3346-3352 accordingly.
